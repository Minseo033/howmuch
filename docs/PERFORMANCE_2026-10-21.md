# 2026-10-21 조회 대기·탭 복귀 성능 개선

## 판단과 적용 범위

사용자가 전달한 운영 QA(리포트 통계 6.2/6.2/7.8초, 마이 통계 약 3.5초)는 수정 전 관측값이다. 이번 작업에서 같은 운영 계정으로 전후 시간을 직접 재측정한 값으로 취급하지 않는다.

효과가 가장 확실한 곳은 선택하지 않은 데이터에 대한 대기, 탭을 바꿀 때의 화면 재생성, 같은 이력의 중복 조회, 전국 카탈로그의 불필요한 상세 정보다. 이 네 경로와 네이티브 시작 전 대기를 수정했다. 화면 전환 시간을 추가로 줄이는 변경은 하지 않았다.

## 데이터 정합성

- 로그아웃·로그인·세션 복원 때 메모리 요청 캐시를 폐기한다. 이전 계정의 늦은 응답은 새 계정의 요약과 섞지 않는다.
- 찜·제보·목표·프로필·방문 변경 성공 시 관련 조회 캐시를 무효화한다. 영수증 multipart 제출도 별도로 무효화한다.
- 조회 중 방문 변경이 생기면 과거 통계 결과를 표시하지 않고 새 조회로 갱신한다. 프로필 수정·계정 관리 복귀는 신선한 TTL 안이어도 다시 확인한다.
- 서버는 승인·방문 삭제·탈퇴 후 visits 캐시를 무효화한다. 이미 진행 중이던 이전 조회는 새 세대의 데이터로 다시 읽어 반환한다.
- 서버 캐시의 256명 상한은 완료된 사용자에 적용한다. 진행 중 조회는 합류할 수 있도록 보존하며, 동시에 대기 중인 사용자가 많으면 일시적으로 이를 넘을 수 있다.
- 지도용 경량 응답과 `/all` 응답은 다른 ETag를 사용한다. 원본 목록을 수정하지 않으며, 이전 서버가 새 경로에 404/405를 반환하면 `/all`로 전환한다.
- 외부 관리자 변경을 앱에 즉시 푸시하는 구독은 추가하지 않았다. 사용자는 탭 재진입·명시적 새로고침·TTL 만료 시 새 값을 조회한다.

선택 기간 우선 표시, 늦은 부가 응답, 탭 유지·미방문 탭 미생성, 마이 재진입 호출 수, 다른 계정의 늦은 응답 차단, 방문 변경 도중 응답 무효화, 저장 목표 즉시 반영, 서버 동시 조회·삭제 무효화, 상세 영업시간 복원, 전국 검색 필드 보존을 자동 검사한다.

## 첫 카탈로그 요청 계측 추가

사용자가 후속 진단 진행을 지시해 `GET /api/stores/catalog`·`GET /api/stores/all`에만 계측을 추가했다. 목록·가격·매장 수·ETag·압축 설정을 바꾸는 최적화는 이번 단계에 포함하지 않는다. 진단 코드가 응답을 통째로 복사하거나 버퍼링하지 않도록 기존 출력 스트림에 즉시 전달한다.

각 응답의 `X-Catalog-Request-Id`는 서버가 새 UUID로 생성한다. 같은 값으로 Render의 `[CatalogTiming] request_id=...` 로그 한 줄을 찾을 수 있다. 클라이언트가 보낸 식별자는 사용하지 않는다. `Server-Timing`에는 첫 애플리케이션 쓰기/flush 직전까지 완료한 단계별 ms를 제공하며, 허용된 웹 출처가 두 헤더를 읽을 수 있도록 CORS 노출 목록에 추가한다.

| 값 | 의미 |
| --- | --- |
| `catalog_lookup` | 공개 카탈로그 조회 전체. 아래의 대기·구성·ETag 시간을 포함하므로 합산하지 않음 |
| `catalog_wait` | 원본 카탈로그 공유 잠금 획득까지의 대기 |
| `catalog_build` | 매장 공개 필드 구성·보정·중복 제거·불변 복사·검색 가능 목록 생성 |
| `catalog_etag` | 전체 공개 목록 JSON 직렬화와 SHA-256 계산 |
| `map_wait` / `map_build` | 지도용 경량 목록 잠금 대기 / 투영 구성 |
| `app_prewrite` | 진단 필터 진입부터 첫 servlet body write/flush 직전까지. 실제 클라이언트 TTFB가 아님 |
| 로그 `app_dispatch_ms` | 필터 진입부터 동기 servlet chain 반환까지 |
| 로그 `app_after_prewrite_ms` | 위 전체 시간에서 prewrite를 뺀 나머지. 후속 JSON 변환·동기 출력 대기·필터 반환 작업을 포함하며 순수 직렬화나 다운로드 시간으로 부르면 안 됨 |
| 로그 `output_bytes` | 앱 출력 스트림에 성공적으로 전달한 바이트 수. 컨테이너 압축·네트워크 전송량/수신 완료를 뜻하지 않음. 문자 writer 경로나 쓰기 실패는 `-1`(미측정/불완전) |
| 로그 `source_cache` / `map_cache` | `miss`: 직접 구성, `shared`: 잠금 대기 중 다른 요청이 구성한 캐시 재사용, `hit`: 이미 준비된 캐시 재사용. 미적용 경로는 `not_checked` |
| 로그 `stores` / `warming_up` | 공개 목록 개수와 원본 조회 시 시작 보강 작업 진행 여부 |

재사용한 캐시에는 build/ETag 단계가 없을 수 있다. 304·빈 응답도 진단 헤더와 로그를 남긴다. 요청 URL 쿼리·헤더·인증 토큰·사용자/매장 식별자·요청/응답 본문은 로그에 넣지 않으며, 예외 시에도 요청별 상태를 제거한다. 현재 대상은 동기 MVC JSON API 두 개로 한정한다.

재테스트에서는 브라우저 Network의 **Waiting/TTFB와 Content Download**를 따로 기록하고 요청 ID로 서버 로그를 연결한다. 서버 로그가 짧은데 TTFB가 길면 필터 진입 전 대기·프록시·시작 구간·네트워크를 별도로 살펴봐야 한다. 서버 build/ETag/wait가 길면 해당 작업을 우선 확인한다. 서버 로그로 DNS/TLS·Render의 요청 수락 전 대기·브라우저 다운로드 완료를 측정할 수는 없다.

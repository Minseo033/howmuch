## 서버 변경 계약

- 본문의 `stores`는 최대 400개이며 모든 항목의 ID·수신 여부를 검증한다. 사용자는 요청 본문에서 UID를 지정할 수 없다.
- 소유한 찜 항목을 모두 확인한 뒤 Firestore WriteBatch를 생성한다. 모르는 매장/다른 계정 매장/중복 ID는 쓰기 전에 거부한다.
- 중복된 이전 찜 문서가 같은 정규 매장 ID에 연결돼 있으면 함께 변경한다. 실제 찜 문서 업데이트 최대 499개와 계정 조건 1개로 배치 한도를 지킨다.
- 찜 목록이 비어 있어도 세 가지 가격 조건은 계정에 저장한다.
- 일반 알림 저장은 명시하지 않은 가격 조건을 덮어쓰지 않는다. 서로 다른 화면의 동시 저장으로 조건이 되돌아가는 것을 방지한다.
- 401 인증 필요, 400 잘못된 입력/한도 초과, 409 찜 항목 불일치, 500 저장 실패. 커밋 성공을 확인한 뒤에만 200과 `success: true`를 반환한다.
- 기존 매장별 저장 API는 유지한다. 새 프런트엔드를 운영에 반영하기 전에 새 백엔드 경로가 배포되어야 한다.

## Skipped / Manual / Risks

- Dart를 지원하지 않는 스킬 `check_state_coverage.ts`는 실행하지 않고 Flutter 상태 테스트와 위 표로 대체했다. 스킬의 상태 모델을 적용해 실패 시 초안 유지·중복 실행 방지·미지원 기능 표시를 보완했다.
- Android/iOS 실기기의 푸시 수신, OS 권한 화면 이동·복귀, 화면 읽기 도구와 키보드 포커스 전면 점검은 수동 검증이 남아 있다. 위젯 테스트나 토큰 등록 200만으로 실제 알림 도착을 보장하지 않는다.
- 새 가격 일괄 API는 단위 테스트에서 소유권·원자적 쓰기·오류 전파를 검증했다. 운영 Firestore에 대한 실제 저장 E2E는 하지 않았다.
- 400개를 초과한 찜 목록은 일괄 저장 한도로 오류가 반환된다. 부분 성공으로 표시하지 않는다. 이 규모 지원이 필요하면 별도 서버 처리 방식이 필요하다.
- 닉네임 비공개 기능은 구현하지 않았다. 과거 저장된 비공개 플래그가 실제 공개 콘텐츠를 숨긴다고 설명하면 안 된다.
- 서버에 이미 존재하는 테스트성 데이터는 클라이언트 목업과 별개다. 운영 데이터를 임의 삭제하지 않았다.
- 기존 의존성의 Swift Package Manager 전환 안내와 Gradle deprecation 안내는 남아 있으나 이번 빌드·테스트의 실패 원인은 아니다.
- 별도 Vercel 배포·운영 별칭 변경은 미실행. Git 푸시와 운영 웹 화면 반영은 구분한다. Render 자동 배포 설정에 따른 후속 반영은 운영 배포 상태로 별도 확인해야 한다.

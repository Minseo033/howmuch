## 구현

- 서버는 먼저 선택 반경을 보수적인 구면 경계로 좁힌 뒤 메뉴·가격 후보를 처리한다. 마지막에는 기존 haversine 거리 검사를 그대로 적용한다. 날짜변경선·극점, 반경 경계, 승인된 무료 메뉴·범위 가격·폐업 제외 및 기존 테마/대체 메뉴 우선순위를 보존한다.
- 전국 주 테마 존재 여부가 기존 대체 테마 선택에 영향을 주는 경우는 유지한다. 이 검사만 공개 카탈로그 객체 기준으로 캐시하고 카탈로그 교체 시 무효화한다.
- 오늘의 픽은 날씨 캐시가 준비되지 않으면 `recommendationBasis=nearby`, `weatherRefreshing=true`와 주변 추천을 먼저 반환한다. 외부 기상 HTTP 응답을 기다리지 않는다. 준비된 날씨는 `recommendationBasis=weather`로 구분한다. 기존 루트 조회 계약은 유지한다.
- 기상 조회는 2개 작업 스레드와 유한 대기열, 같은 지역/예보 시각의 진행 요청 공유, 성공/실패 TTL 및 최대 캐시 크기로 제한한다. 거절·실패·동기/비동기 완료 경합과 출처 데이터의 비정상 온도/시각을 검사한다.
- 앱은 추천 카드를 먼저 표시한다. 서버 기상 갱신은 2초 간격 최대 4회만 확인하고, 기기 보조 날씨 역시 카드 표시와 분리한다. 보조 기온을 받았다는 이유로 거리 기반 추천을 날씨 기반으로 바꾸어 표시하지 않는다.
- 1분 이내 정확히 같은 좌표·반경·날짜의 캐시만 즉시 표시한다. 갱신 중에도 기존 카드를 유지하고, 위치·반경·날짜·요청 세대 또는 화면 생존 여부가 달라진 뒤 도착한 응답은 적용하지 않는다.
- 명시적 새로고침·실패 후 재시도, 날씨 없는 로컬 추천의 접근성 버튼/선택 상태를 보존한다.

## 추천 계산만 분리한 비교

로컬 번들 11,385개를 이미 읽은 상태에서 날씨 입력을 고정했다. 서울·인천·부산 × 맑음/비 × 1/3km의 12개 사례를 각각 7회 실행했다. 수정 전후 추천 JSON SHA-256이 전 사례에서 동일했다.

사례별 중앙값들의 중앙값은 68.915958ms에서 9.141208ms로 약 86.7% 감소했다. 이 값은 서버 내부 추천 선택 계산만 포함하며 카탈로그 첫 구성·외부 날씨·네트워크·JSON 전송·화면 표시 시간을 포함하지 않는다. 전국 자료나 가격 규칙을 줄여 얻은 결과가 아니다.

재현: `cd howmuch_backend && ./gradlew todaysPickBenchmark`. 운영 Firestore/HTTP 호출 없이 번들로 비교한다.
